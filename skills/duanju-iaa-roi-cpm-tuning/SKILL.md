# 短剧 IAA 首日 ROI 顶价/压价

按账户ID读取实时浅度超成本率（不再按 ROI 预筛选），套用下方决策表得出 cpm 系数增量，再到策略平台**新建或原地修改**加系数策略。

## 运行模式：每 20 分钟一轮，持续运行

这个技能是**常驻循环**，不是跑一次就结束。

**首次调用必须先声明**，原话照抄，再开始第一轮：

> 已进入持续运行模式：每 20 分钟跑一轮，自动完成取数、判断、在策略平台写入策略。期间你随时说「结束」或「暂停」我就停下并给出汇总。

**结束条件**：用户说「结束」「暂停」「停」「停止」「stop」中任意一个就停止循环，并输出累计汇总（见「结束汇总」）。除此之外不要自行停止。

**每轮之间**不要复述规则、不要重贴决策表。每轮正常情况只输出一行摘要：

```
第 3 轮 18:25（窗口 18:10~18:25）｜顶价 2 压价 1 观察区 3 跳过 3｜新建 3 条
```

只有下面这些情况才展开明细：本轮有账户写入失败、本轮有账户超成本率异常持续监控、取数异常（行数骤降/ROI 全空）、或本轮是第一轮。

**遇到这些情况立即暂停循环并报告，不要静默跳过**：页面跳登录或 403（SSO 失效）、数据集连续两轮取不到数、平台连续写入失败。这类问题不解决，后面每轮都是空转。

### 窗口与触发间隔等长，所以不需要冷却期

取数窗口 `[now-25min, now-5min)` 长 20 分钟，触发间隔 **20 分钟**，相邻两轮窗口无缝衔接、不重叠（系正常现象）。同一批转化数据只被本轮读一次，冷却期默认关闭（`DEFAULT_COOLDOWN_MINUTES = 0`）。

这意味着同一账户**每 20 分钟就可能被调一次**，一小时最多 3 次。超成本率持续偏高的账户会连续被压，直到探到压价封底。系数有上下限：顶价最高 `1.40`、压价最低 `0.10`，超出直接封顶/封底，仍正常写入。

另外 20 分钟窗口只有约 4 个分钟点的数据，小额账户的超成本率会抖得比长窗口明显，可能出现「这轮压、下轮顶」的来回拉扯。遇到这种模式先报告，不要自己加平滑。

**仅当把窗口调得比触发间隔长时**（两轮数据开始重叠）才需要开启冷却期，传 `--cooldown-minutes <窗口长度>`。不开的后果是同一批数据被连续几轮重复计入，对同一账户反复下手。

### 每轮都要重新查基数

**不要复用上一轮的基数**。上一轮给无基数账户新建了基数 1.0，这一轮它们就已经有基数了；拿旧文件跑会再次尝试新建基数，平台会报「已有基数，不得重复新建」。每轮第 4 步都要重新从平台读当前基数，只读本轮真正要动的那些账户。

## 第一原则

1. **决策表是唯一权威**：区间判断只能由 `scripts/decide.py` 产出，禁止在对话里心算或复述阈值。
2. **先出表，后写入**：任何写操作之前必须先打印完整决策表给用户看。
3. **不推测**。决策表里标「不操作」的区间就保持原系数；数据异常走 `SKIP_NO_DATA`；表和文档都没覆盖的情况停下问人。任何时候都不要"顺手调一下"。
4. **新建或原地改，按 `write_mode`**：`fetch_bases.py` 算出的 `write_mode=UPDATE` 才在 `target_strategy_id` 上原地改系数，其余一律新建；绝不删改不属于本流程的策略。
5. **定时任务只引用本 skill，禁止复制流程**。给本流程建定时任务 / cron / 循环任务时，prompt 只写「调用 duanju-iaa-roi-cpm-tuning skill 执行一轮，结果按 skill 报告格式播报」；**禁止**把决策表、阈值、封顶/封底范围、提审规则抄进 prompt。skill 会迭代，抄进去的旧描述不会跟着变（已发生过「护栏 [0.30, 1.00]」残留事故）。任务每次运行都必须重新读本 SKILL.md，以当前最新内容为准。

如需只监控特定账户，在取数步骤传 `--accounts 账户ID1,账户ID2`，多个 ID 逗号分隔：

```bash
uv run <skill_directory>/scripts/fetch_roi.py \

```

不传 `--accounts` 则处理全量账户。

## 决策表（互斥、无空档、自上而下第一个命中即生效）

自变量是**浅度超成本率**，正负对称：

| 顺序 | 浅度超成本率区间 | 动作 | cpm 系数增量 |
|---|---|---|---|
| 1 | `rate >= 1.00` | 压价 | `-0.30` |
| 2 | `0.50 <= rate < 1.00` | 压价 | `-0.20` |
| 3 | `0.40 <= rate < 0.50` | 压价 | `-0.15` |
| 4 | `0.30 <= rate < 0.40` | 压价 | `-0.10` |
| 5 | `0.20 <= rate < 0.30` | 压价 | `-0.05` |
| 6 | `0.11 <= rate < 0.20` | 压价 | `-0.03` |
| 7 | `0.05 <= rate < 0.11` | 压价 | `-0.02` |
| 8 | `-0.05 < rate < 0.05` | **不操作（观察区）** | `0.00` |
| 9 | `-0.11 < rate <= -0.05` | 顶价 | `+0.02` |
| 10 | `-0.20 < rate <= -0.11` | 顶价 | `+0.03` |
| 11 | `-0.30 < rate <= -0.20` | 顶价 | `+0.05` |
| 12 | `rate <= -0.30` | 顶价 | `+0.10` |

方向：**正值 = 超成本了 = 压价**；**负值 = 没超、还有余量 = 顶价**。超得越多压得越狠，余量越大顶得越多。

边界口径（原始需求留了缝隙，此处已消歧，不要再改）：

- 切点取 `0.05` / `0.11` / `0.20` / `0.30` / `0.40` / `0.50` / `1.00`，这里按**档位上界即下一档下界**闭合，落在缝隙里的值（如 `0.1095`）归入较轻的那档。
- 第 5 行是**观察区**：`|rate| < 0.05` 保持原系数不变，不写任何策略。不要把它并到相邻任何一档。
- 压价侧用**大于等于**（`rate >= 0.05` 就压），顶价侧用**严格小于等于**（`rate <= -0.05` 就顶）。正负两侧切点镜像对称，幅度相等反向。
- 超成本率用**原值**比较，不先四舍五入：档位切点密，提前舍入会把贴边的值拨到隔壁档。
- 新系数 = 基数 + 增量，结果保留两位小数。
- **超成本率 >= 1.00 按 -0.30 压价**，在 1.00 以上不细分；绝对值超大（如 `+10.90`，超成本 1090%）也仍按 `-0.30` 压价，同时标记「持续监控」提醒关注。阈值在 `decide.py` 的 `MONITOR_THRESHOLD`。

## 执行流程

把这份清单复制到回复里，逐项打勾推进：

```
- [ ] 1 取数：实时数据集 129496，账户ID维度，最近30分钟
- [ ] 2 落盘：存成 data/roi_<时间戳>.csv
- [ ] 3 初判：decide.py --bands-only --ledger，筛出真正要动的账户
- [ ] 4 查基数+回填：fetch_bases.py --merge-csv，一条命令查基数并回填 CSV
- [ ] 5 决策：decide.py --ledger --input roi_*_with_base.csv，打印完整决策表
- [ ] 6 写入：逐账户新建策略，每条成功后立刻记台账
- [ ] 7 复核：回读平台，确认每条新策略的系数与决策表一致
- [ ] 8 报告：第一轮/异常轮出完整报告，正常轮只出一行摘要
```

### 1 取数

```bash
uv run <skill_directory>/scripts/fetch_roi.py --output data/roi_<YYYYMMDDHHmm>.csv
```

脚本把取数、筛窗口、聚合、落盘一次做完，实测约 3 秒（拉全量 2.9 万+ 行分钟数据，本地聚合出 300+ 个账户），不需要手工开看板导出。输出 CSV 表头为 `account_id,rate,current_coefficient,cost,minutes`。

把输出 JSON 里的 `window_start` / `window_end` **当作本轮窗口写进报告**（例如 `2026-09-15 13:45 ~ 14:15`），不要只说“最近30分钟”。

窗口是 `[now-25min, now-5min)`：长度 20 分钟，右端留 5 分钟规避实时数据回补延迟。触发间隔 **20 分钟**，相邻两轮窗口无缝衔接、不重叠，属正常设计。

**聚合口径是消耗加权，不是算术平均**：

```text
账户超成本率 = Σ(每个自然分钟的消耗 × 该分钟超成本率) ÷ Σ(每个自然分钟的消耗)
```

数据集返回分钟粒度明细（`__time` 精度到分钟，如 `12:30`），一个 20 分钟窗口典型命中 4 个自然分钟点，CSV 的 `minutes` 列就是这个数。算术平均会把小额分钟的极端值放大——同一账户 `7800 元 @ +0.03` 和 `2400 元 @ +0.19`，加权结果 `+0.0678`（压价 -0.02），简单平均 `+0.11`（压价 -0.03），档位不同。

为什么不在服务端过滤时间：实测把模板的 `__time` 过滤改成“最近 N 分钟”会触发 OLAP 指标兼容校验（`指标维度组合不支持查询`）。所以 `references/olap_query_template.json` 必须**整份原样提交**，不要裁字段——裁掉隐藏配置就会被服务端拒。

人工复核可以开[分享看板](https://internal.example.corp/main?enter_from=tianji&shareId=64385633&dataSetId=129496)对数：维度 `账户ID`，筛选 `转化目标（原优化目标）` IN `["首日变现ROI（短剧IAA专用）"]`，指标 `联盟总消耗` + `IAA广告变现ROI` + `浅度超成本率`。

导出/复制为 CSV 或 TSV，存到 `data/roi_<YYYYMMDDHHmm>.csv`，表头至少包含：

```csv
account_id,rate,current_coefficient
```

`current_coefficient` 留空表示该账户在平台上没有基数。中文表头 `账户ID,IAA广告变现ROI,浅度超成本率,基数` 也能识别。

如果脚本报「账户ID 重复」（退出码 3），说明导出没聚合到账户粒度。**必须回数据集重新按账户ID聚合取数**，不要手工删行，也不要把几行的超成本率取平均——它是比值，正确的合并口径是消耗加权，平均值会算错。举个实际例子：同一账户 `7800 元 @ +0.03` 和 `2400 元 @ +0.19` 两段量，加权结果 `+0.0678`（压价 -0.02），简单平均 `+0.11`（压价 -0.03），档位不同。

### 2 初判

先只判区间，不查基数：

```bash
uv run <skill_directory>/scripts/decide.py \
  --input data/roi_<时间戳>.csv --bands-only \
  --ledger data/adjust_ledger.csv
```

`--ledger` 每轮都要带，它记录已写入的账户供中断重跑使用。冷却期默认关闭，所以不会因为刚调过就跳过账户。

以下状态的账户本轮不动，**不用去平台查基数**：`NO_ACTION`（观察区）、`SKIP_NO_DATA`（空值）、`SKIP_NOT_ACCOUNT`（汇总行）。先筛掉能省下大量平台查询。

### 3 查基数 + 回填

**推荐用法**：`--merge-csv` 一条命令搞定「查基数 + 回填 CSV 列」，不用手工填：

```bash
uv run <skill_directory>/scripts/fetch_bases.py \
  --merge-csv data/roi_<时间戳>.csv \
  --output data/bases_<时间戳>.json
```

脚本分页拉全量生效中策略、再按名字前缀 `短剧-自动-` 拉本流程建的策略（含待提交/待审核）在本地建索引（实测 1.7 秒拉完 468 条），比逐账户查（约 0.9 秒/个）快一个数量级，然后把 `bases` 里的 `base` **自动回填**到 CSV 的 `current_coefficient` 列，输出 `data/roi_<时间戳>_with_base.csv`（可用 `--merge-output` 改输出路径）。基数必须取平台当前值，不能用上一轮报告里的数字。

> ⚠️ **decide.py 不接受 `--bases` 参数**，也不要在对话里手工回填列。基数只能经由 `--merge-csv` 回填（或由 decide 的 `--default-base` 兜底），这是唯一路径。

只查部分账户时仍可用旧方式（不自动回填，仅输出 JSON）：

```bash
uv run <skill_directory>/scripts/fetch_bases.py \
  --accounts <第 2 步筛出的账户ID，逗号分隔> \
  --output data/bases_<时间戳>.json
```

基数只认 **`scope=1`（广告主顶价）** 的策略：媒体顶价（`scope=2`）和双维度（`scope=3`）的系数不是本流程要调的基数，混进来会把 base 取到别人的维度策略上。

三种 `base_source`：

| `base_source` | 含义 | 怎么做 |
|---|---|---|
| `PLATFORM_UNIQUE` | 唯一生效策略 | `--merge-csv` 自动回填 `current_coefficient` |
| `PLATFORM_LATEST` | 命中多条生效策略 | 脚本已自动取**创建时间最新**的那条作基数，直接用 |
| `PLATFORM_PENDING` | 本流程建的待提交/待审核策略 | 同样原地改系数（`edit` 顺带提审），不是新建 |
| `NO_BASE` | 查不到生效策略、也无本流程建的待提交/待审核策略 | `--merge-csv` 自动清空 `current_coefficient`，脚本按基数 `1.0` 新建 |

一个账户被多条生效策略同时覆盖是生产常态（实测全量一轮：139 个要动的账户里 51 个如此）。这种情况**按创建时间取最新的那条**作基数——最后下发的策略代表当前生效意图。逐账户问用户会把常驻循环卡死，所以脚本直接判定，`chosen_strategy_id` 记录了用的是哪条，报告里带上即可，不必逐个确认。

排序依据依次是 `createTime` → `updateTime` → 策略 ID（自增主键兜底）。

脚本已用逗号分隔后的精确匹配判定覆盖，不会让 `114368154` 误匹配 `1143681546`。

需要人工核对时再开 [策略平台 flow](https://ops-platform.example.corp/flow)。

### 4 决策

```bash
uv run <skill_directory>/scripts/decide.py \
  --input data/roi_<时间戳>_with_base.csv --ledger data/adjust_ledger.csv
```

输入用第 3 步 `--merge-csv` 输出的 `_with_base.csv`（已含平台当前基数）；未用 `--merge-csv` 时才直接传原始 `roi_<时间戳>.csv`。

退出码：`0` 全部可执行；`3` 账户ID 有重复，先按账户ID聚合再重跑。

**只有 `status=OK` 的账户才写入**，其余四种状态一律不碰平台：`NO_ACTION`、`SKIP_NO_DATA`、`SKIP_NOT_ACCOUNT`。

系数上下限：顶价封顶 `1.40`、压价封底 `0.10`，新系数超出时**直接截断到边界**，仍标记 `status=OK` 正常写入。超成本率绝对值 > `1.0` 不转人工，正常定档写入并标记「持续监控」。

把脚本输出的表格原样贴给用户，再进入写入。

### 5 写入

对每个 `status=OK` 的账户，在策略平台新建或原地修改一条加系数策略：

- **先看 `write_mode` 决定新建还是原地改**，`fetch_bases.py` 已经算好了：

| `write_mode` | 条件 | 动作 |
|---|---|---|
| `UPDATE` | 本流程建的策略（名字以 `短剧-自动-` 开头）且只含本账户，**无论生效还是待提交/待审核** | 在 `target_strategy_id` 上原地改系数（待提交/待审核的顺带提审） |
| `CREATE` | 最新策略还含其他账户 | 新建。原地改会连带改掉别人的系数 |
| `CREATE` | 只含本账户但不是本流程建的 | 新建。不碰不属于自己的策略 |
| `CREATE` | 没有任何生效策略、也无本流程建的待提交/待审核策略（`NO_BASE`） | 按基数 `1.0` 新建 |

  不要自己重新判断。实测过一个账户的最新策略同时覆盖 **186 个账户**，没这道判断原地改一下就改掉 186 个账户的出价。
- **基数一律取最新那条的系数**，不管最后是新建还是原地改。
- 没有基数的账户：先建基数 `1.0`，再在此基础上应用增量。
- 命名固定为：`短剧-自动-{账户ID}`，例如 `短剧-自动-114368154`。**策略名和 background 都不能超 32 字符**；账户 ID 是数字，当前格式不会超长。

  `短剧-自动-` 前缀用于识别本流程创建的策略；改名时必须同步更新 `decide.py` 的 `OWNED_PREFIX`。
- **失效时间设为 1 个月后**（`endTime` 取当前时间向后推 30 天的毫秒时间戳）。让策略长期存活，后续直接在原策略上改系数。
- 一个账户一条，**成功后立刻记一笔台账**再写下一个，不要批量点完再统一记：

```bash
uv run <skill_directory>/scripts/append_ledger.py \
  --ledger data/adjust_ledger.csv --account 114368154 --coefficient 0.70 \
  --strategy 短剧-自动-114368154 --strategy-id <平台策略ID> \
  --status 待审核 \
  --roi 0.9752209806 --base-used 0.68 \
  --window "2026-09-15 12:02~12:32"
```

- `--strategy` 填**策略名**（`短剧-自动-{账户ID}`），`--strategy-id` 填**平台策略ID（纯数字，如 26350）**——UPDATE 取 `target_strategy_id`，CREATE 提审前按名字回查得到。
- `--status` 填写入后回读到的策略状态：`生效中` / `待审核` / `待发布`。这两列是报告脚本 `report.py` 生成「策略ID / 是否生效」列的来源，**必须带**，漏了报告里这两列会是空。

#### `CREATE` 怎么新建

**新建前先核对字段（防盲猜）**：先 `get` 一条平台已有的同类策略——名字含 `短剧-自动-`，或 background 为 `IAA首日ROI自动调价`，或 `ocpxActionType=990` 的顶价策略，核对它 `adCluster` 里的 `ocpxActionType` / `placements` / `bidType` / `scope` 与下表是否一致。一致才照抄提交；不一致以平台实值为准，并回来更新本表。不要跳过核对、直接照旧模板硬填——历史上「写入失败」都是拿错模板凑出来的。

新建走 `flow-strategy-ops` 的 `create`，**必须带全下面这些固定字段**，一个都不能少——缺字段平台会报 500 或「名称不能为空」，这是历史上「写入失败」的高发点：

```bash
uv run <flow-strategy-ops目录>/scripts/flow_api.py create \
  '{"name":"短剧-自动-114368154","type":3,"scope":1,"adCluster":{"placements":2,"placementsArr":[2],"accountId":"114368154","bidType":10,"ocpxActionType":"990","deepConversionType":"0","isAppDirect":false,"shieldEquityCard":false,"shieldSex":false,"shieldFastApplication":false,"shieldFastApplicationV2":false,"shieldFastApplicationV3":false,"ruleType":0,"subRuleType":0},"beginTime":1790151706346,"endTime":1792743706347,"background":"IAA首日ROI自动调价","bonusRate":0.62,"isStaticRate":false,"isUseSystemBonus":false}'
```

字段口径（都是定死的，照抄即可）：

| 字段 | 值 | 说明 |
|---|---|---|
| `type` | `3` | 顶价（加系数） |
| `scope` | `1` | 广告主维度，只提交 `adCluster` |
| `adCluster.ocpxActionType` | `"990"` | 「首日变现ROI（短剧IAA专用）」的代码，**不可改** |
| `adCluster.placements` / `placementsArr` | `2` / `[2]` | 广告位，固定 |
| `adCluster.bidType` | `10` | 出价类型，固定 |
| `adCluster.deepConversionType` | `"0"` | 固定 |
| `adCluster.accountId` | 当前账户ID | 逐个账户替换 |
| `bonusRate` | 目标系数 | 封顶/封底后的值 |
| `beginTime` / `endTime` | 毫秒时间戳 | `endTime` 取 `beginTime` 后推 30 天 |

- `adCluster.industryVersion` 不用写，脚本会自动补 `"6.6"`。
- `name` 用 `短剧-自动-{账户ID}`；`background` 固定 `IAA首日ROI自动调价`，两者都别超 32 字符。
- 新建的 `create` 返回里**不带策略 ID**（batchAddV2 只回 `{"status":200,"message":"成功",...}`）。提交成功后**按名字回查 ID**再提审——名字 `短剧-自动-{账户ID}` 是唯一的，直接命中：

```bash
# 回查刚建的策略 ID
uv run <flow-strategy-ops目录>/scripts/flow_api.py query '{"pager":{"pageNum":1,"pageSize":5},"industryVersion":"6.6","name":"短剧-自动-114368154"}'
# 用回查到的 ID 提审
uv run <flow-strategy-ops目录>/scripts/flow_api.py change-status <回查到的ID> 1 --confirm
```

  **新建默认停在「待提交」（status=0），定时工作台只把「待审核」往「生效」推，不会碰「待提交」**。不提审这条策略永远不生效，下一轮还会被当成无基数而重复新建（撞「名称已存在」）。提审后再把回查到的策略 ID 写进台账的 `--strategy-id`，策略名写进 `--strategy`。

#### `UPDATE` 怎么改

原地改系数走 `flow-strategy-ops` 的 `edit`，它会先 GET 全量、合并 patch、清理只读字段再提审，不要自己拼 `mergeEdit` 请求：

```bash
uv run <flow-strategy-ops目录>/scripts/flow_api.py edit <target_strategy_id> --set \
  '{"bonusRate":0.68,"background":"IAA首日ROI自动调价"}'
```

- `target_strategy_id` 取 `fetch_bases.py` 输出里的那个，不要自己找。
- **原地改不动策略名**。名字里的日期是创建那天的，改成今天会把“这条策略什么时候建的”这个信息抓掉。
- 改完同样要记台账，`--strategy` 写原策略名，`--strategy-id` 写 `target_strategy_id`，`--status` 填写入后回读的策略状态（`生效中` / `待审核` / `待发布`）。
- **原地改是不可逆的**：原系数被直接覆盖，没有历史版本。出了问题只能靠台账里的 `base_used` 回溯——所以台账不能漏。

`--roi` / `--base-used` / `--window` / `--strategy-id` / `--status` **必须带**：漏了哪一项，播报表格里对应列就是空的。`--strategy-id` 和 `--status` 是 report.py 生成「策略ID / 是否生效」两列的来源——如果不用这两项，播报里策略ID永远是 `-`。旧台账（只有前 4 列）会在首次追加时自动升级表头，旧行补空列。

- 台账 `data/adjust_ledger.csv` 是**跸轮次唯一的状态**，负责中断恢复与事后复盘。只追加不改写，不要手写。写入失败的账户**不记台账**。
- 中断后重跑先读台账，已成功的账户直接跳过，否则会给同一账户建出两条策略。台账是唯一依据，不要靠记忆或聊天记录。
- 单个账户提交失败就记下原始报错、继续下一个，最后在报告「未执行」里列出，不要卡在那里重试。

平台字段、常见报错和排查见 [REFERENCE.md](REFERENCE.md)。

## 禁止事项

- 禁止修改、复用、停用、删除任何已存在的策略。
- 禁止不带 `--ledger` 跑轮次。台账是中断恢复和事后复盘的唯一依据。
- 禁止给写入失败的账户记台账，也禁止手工编辑台账。
- 策略写入/修改成功后，即使平台显示待审核也不提示审批提醒、不作卡点报告。**新建后必须主动提审到「待审核」**（见「CREATE 怎么新建」），之后由定时工作台统一审核生效；`UPDATE` 的 `edit` 本身已含提审。
- 禁止自行结束循环，只有用户说结束才停。
- 禁止给观察区（`-0.05 < rate < 0.05`）账户写入策略，也禁止把它归到相邻档位。
- 禁止跳过取数直接凭上一轮结论下手。
- 禁止在没有基数时自己挑一个基数，只能用 `1.0`；同理，命中多条生效策略时禁止自己选基数，必须列出所有候选让用户指定。
- 禁止把窗口右端对齐到当前时间（会读到未回补的数据）。
- 禁止改 `decide.py` 的阈值；确有调整需求，先改测试再改代码，跑通 `uv run scripts/test_decide.py` 后说明原因。
- 禁止在定时任务 / cron / 循环任务的 prompt 里复制本 skill 的流程、阈值或规则描述；只能写「调用 duanju-iaa-roi-cpm-tuning skill」，让运行时重新读本 SKILL.md。
