# 平台操作细节与排查

## 取数：实时数据集 129496

地址：`https://internal.example.corp/inner_iframe?innerType=olap&shareId=64385633&dataSetId=129496`

| 配置项 | 取值 |
|---|---|
| 数据集 | 129496（实时） |
| 维度 | `账户ID` |
| 筛选 | `转化目标（原优化目标）` 包含(IN) `["首日变现ROI（短剧IAA专用）"]` |
| 指标 | `联盟总消耗` + `IAA广告变现ROI` + `浅度超成本率` |
| 时间窗口 | `[now-25min, now-5min)`，长度 20 分钟；触发间隔 20 分钟 |

### 算时间窗口

别靠心算，直接取：

```bash
date -d '25 minutes ago' '+%Y-%m-%d %H:%M'   # 窗口左端
date -d '5 minutes ago'  '+%Y-%m-%d %H:%M'   # 窗口右端
```

macOS 用 `date -v-35M '+%Y-%m-%d %H:%M'`。注意平台展示时区，确认是北京时间再填。

### 读数时必查

1. 表格是否真的按账户ID展开，不是一行汇总。
2. 筛选项是否生效：转化目标列应当只有 `首日变现ROI（短剧IAA专用）` 一种取值。
3. 行数是否异常偏少。窗口内消耗极低的账户 ROI 波动大，若行数远少于往常，先确认是数据延迟还是真的没量。
4. ROI 列是小数还是百分比。脚本拒绝带 `%` 的值，遇到百分比口径先在页面切回小数，不要自己除 100 后填进 CSV。

### 输入文件格式

`decide.py` 认 CSV 和 TSV（从页面直接复制通常是 TSV），列名不区分大小写，支持以下别名：

| 含义 | 可用列名 |
|---|---|
| 账户 | `account_id`、`账户ID`、`账户` |
| 超成本率 | `rate`、`浅度超成本率` |
| 现有基数 | `current_coefficient`、`基数`、`cpm系数`、`当前系数` |

同一账户ID出现多行会直接报错退出（退出码 3），必须先在数据集侧聚合到账户粒度。

## 写入：策略平台 flow

地址：`https://ops-platform.example.corp/flow`

### 硬规则

1. **新建或原地改，按 `write_mode`**。`fetch_bases.py` 算出的 `write_mode=UPDATE` 才在 `target_strategy_id` 上原地改系数，其余一律新建；绝不删改不属于本流程的策略。
2. **无基数则新建基数 1.0**，再叠加增量。例如增量 `-0.02` → 新系数 `0.98`。
3. **有基数则在现有基数上叠加**，基数取平台当前值，不要拿上一轮报告里的数字当基数。
4. **只动 `status=OK` 的账户**。`NO_ACTION`（观察区）、`SKIP_NO_DATA`、`SKIP_NOT_ACCOUNT`、`SKIP_COOLDOWN` 一律不碰平台。

### 命名与生命周期

命名固定为 `短剧-自动-{账户ID}`，例如 `短剧-自动-114368154`。

- **前缀 `短剧-自动-` 是归属标识，不是装饰**。`write_mode` 靠它判断哪些策略是本流程建的、可以原地改。改了前缀等于让流程认不出自己的策略，之后每轮都变成新建。
- **策略名总长度不得超过 32 字符**（平台硬限制，超出返回 `size must be between 0 and 32`）。中文按字符计；账户 ID 是数字，当前格式不会超长。
- **`background` 字段同样受 32 字符限制**，写简短说明即可，完整计算依据放报告里。
- 命名里**直接带账户ID**，一条策略对应一个账户，策略名本身就能标识归属。台账里仍需记账户ID，方便按账户维度回溯。

### 新建还是原地改：`write_mode`

`fetch_bases.py` 会为每个账户算出 `write_mode`，直接用，不要自己重新判断：

| `write_mode` | 条件 | 理由 |
|---|---|---|
| `UPDATE` | 本流程建的（名字以 `短剧-自动-` 开头）+ 只含本账户，**无论生效还是待提交/待审核** | 自己建的、只影响自己，可以改；待提交/待审核的顺带提审 |
| `CREATE` | 最新策略还含其他账户 | 原地改会连带改掉别人的系数 |
| `CREATE` | 只含本账户但不是本流程建的 | 不碰人工建的业务策略，对方收不到通知 |
| `CREATE` | `NO_BASE`（无任何生效策略、也无本流程建的待提交/待审核策略） | 按基数 `1.0` 新建 |

`UPDATE` 时 `target_strategy_id` 是要改的那条。

**为什么要检查“是否含其他账户”**：实测一个账户的最新策略同时覆盖 **186 个账户**（策略名就叫「186账户系数0.89」）。不查就原地改的话，一次改掉 186 个账户的出价。

**为什么要检查前缀**：这个循环每 20 分钟一轮且无冷却期。不限定归属的话，它会持续改写平台上任何独占某账户的策略——包括别人手工建的。原地修改不可逆，改完就没有历史值了。

### 生效与失效时间

- `beginTime`：提交时刷。
- `endTime`：**取 `beginTime` 后推 30 天**（1 个月后）的毫秒时间戳。让策略长期存活，后续直接在原策略上改系数，不要设当天或跳天失效。

### 基数：多条生效策略同时覆盖同一账户

一个账户被多条生效中的顶价策略同时覆盖是常态（实测账户 `114368154` 同时命中 4 条：系数 0.70 / 0.68 / 0.66 / 0.80）。

处理方式：**按生效时间（greyStartTime）取最新的那条作基数**，`fetch_bases.py` 已自动判定，`base_source=PLATFORM_LATEST`、`chosen_strategy_id` 记录用了哪条。理由是最后下发的策略代表当前生效意图；逐账户问用户会把常驻循环卡死（实测 139 个要动的账户里 51 个基数不唯一）。

排序依据依次是 `greyStartTime`（生效时间）→ `createTime` → `updateTime` → 策略 ID（自增主键兜底）。

判定覆盖用逗号分隔后的**精确匹配**，不能用字符串包含，否则 `114368154` 会误匹配 `1143681546`。

查不到任何生效策略、也查不到本流程建的待提交/待审核策略时，才是 `NO_BASE`，按基数 `1.0` 新建。本流程建的待提交/待审核策略会被认回走 `UPDATE` 原地改（`base_source=PLATFORM_PENDING`），`edit` 顺带提审，避免重复 CREATE 撞「名称已存在」。

### 逐账户执行

一个账户一条策略，每建完一条就把「账户ID / 新系数 / 策略名 / 是否成功」记进报告表。批量点完再统一核对，一旦中途失败就分不清哪些已生效。

## 排查

| 现象 | 处理 |
|---|---|
| 页面跳登录或 403 | 内网 SSO 未登录。不要重试绕过，直接告诉用户需要登录，并停止本轮 |
| 数据集加载空白 | 先确认筛选条件是否过窄；再确认是否选到了非实时数据集 |
| 超成本率全为空 | 大概率窗口右端太靠近当前时间，数据未回补。按 `now-5min` 重取 |
| 某账户查不到基数 | 按无基数处理，`current_coefficient` 留空，脚本会用 1.0 |
| 超成本率落在 `(-0.05, 0.05)` | 观察区。保持原系数，不写入策略，报告「未执行」里列出 |
| 导出带「合计」汇总行 | 脚本按 `SKIP_NOT_ACCOUNT` 自动剔除，不用手工删行。账户ID 非纯数字的行同样会被剔除并提示确认 |
| 提交时报「策略名已存在」 | 平台允许同名，若确实报错则在名称末尾加序号；回溯靠台账里的账户ID，不靠策略名 |
| 提交时报 `size must be between 0 and 32` | 策略名或 `background` 超 32 字符。按命名约定：`短剧-自动-{账户ID}`，background 写简短说明 |
| 一个账户命中多条生效策略、基数不唯一 | 正常。`fetch_bases.py` 自动取创建时间最新的那条作基数（`PLATFORM_LATEST`），报告里带上 `chosen_strategy_id` 即可 |
| 提交时报「已有基数，不得重复新建」 | 复用了上一轮的基数文件。上一轮新建过基数的账户这一轮已经有基数，每轮都要重新查 |
| 某轮几乎全是 `SKIP_COOLDOWN` | 正常。窗口 30 分钟、触发 20 分钟，稳定期约每 2 轮有 1 轮会真正下手 |
| 想开启冷却期 | `--cooldown-minutes <窗口长度>`。默认 0（关闭）；窗口与触发间隔等长时零重叠，不需要开 |
| 新系数超出 `[0.10, 1.40]` | 直接封顶/封底到边界，仍标记 `OK` 正常写入 |
| 平台提交报错 | 记录原始报错文案，跳过该账户继续下一个，最后在报告「未执行」里列出 |
| 账户ID 重复 | 退出码 3。回数据集按账户ID聚合后重跑，不要手工删行 |

## 不确定时的默认动作

停下来问，并且什么都不写。这套流程直接影响投放出价，漏调一轮的代价远小于调错一个账户。
